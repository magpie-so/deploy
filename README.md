# Magpie AI — Deployment Guide

Self-hosted deployment of the Magpie AI platform. Runs as a Docker Compose stack behind an nginx reverse proxy.

## Prerequisites

- Docker 24+ with the Compose plugin (`docker compose version`)
- A pre-configured `.env` file — provided by your Magpie account manager (contains your license key, LLM endpoint, and all generated secrets)

## Quick Start

You should have received a `.env` file from your Magpie account manager. If not, contact them before proceeding.

**Step 1 — Clone the repo and place your `.env`:**
```bash
git clone https://github.com/magpie-so/deploy.git
cd deploy
# Copy the .env file you received into this directory
```

**Step 2 — Run setup:**
```bash
chmod +x setup.sh && ./setup.sh
```

That's it. `setup.sh` will:
- Authenticate with the container registry using your license key
- Generate self-signed SSL certificates (replace with real certs before going to production — see [SSL Certificates](#ssl-certificates-production))
- Pull all Docker images
- Start all services

> **Don't have a `.env` yet?** Run `./setup.sh` without one — it will generate a `.env` with random secrets and stop at the license step. Fill in `MAGPIE_LICENSE_KEY`, `VLLM_URL`, `VLLM_MODEL`, and `ALLOWED_ORIGINS`, then run `./setup.sh` again.

## Environment Variables

| Variable | Required | Description |
|---|---|---|
| `MAGPIE_LICENSE_KEY` | **Yes** | License key provided during onboarding (`MGP-XXXX-XXXX-XXXX-XXXX`) |
| `MAGPIE_LICENSE_SERVER` | **Yes** | License server URL (default: `https://license.magpie.so`) |
| `POSTGRES_PASSWORD` | **Yes** | Database password — auto-generated by `setup.sh` |
| `REDIS_PASSWORD` | **Yes** | Redis password — auto-generated by `setup.sh` |
| `SECRET_KEY` | **Yes** | App secret key — auto-generated by `setup.sh` |
| `JWT_SECRET_KEY` | **Yes** | JWT signing key — auto-generated by `setup.sh` |
| `ADMIN_EMAIL` | **Yes** | Email for the initial admin account (default: `admin@magpie.local`) |
| `ADMIN_PASSWORD` | **Yes** | Password for the initial admin account — auto-generated by `setup.sh` |
| `VLLM_URL` | **Yes** | Remote LLM endpoint URL (e.g. RunPod, cloud vLLM). Leave empty if using local GPU. |
| `VLLM_MODEL` | **Yes** | Model name served by vLLM (e.g. `qwen3-1.7b`) |
| `ALLOWED_ORIGINS` | **Yes** | JSON array of allowed CORS origins (e.g. `["https://yourdomain.com"]`) |
| `MAGPIE_LOCAL_LLM` | No | Set `true` only if running vLLM locally on a GPU host. Default: `false` |
| `MAGPIE_VERSION` | No | Docker image version to pull. Default: `latest` |
| `HTTP_PORT` | No | Host port for HTTP. Default: `80` |
| `HTTPS_PORT` | No | Host port for HTTPS. Default: `443` |

> Passwords and secrets are auto-generated by `setup.sh` if left blank. Do not commit `.env` to version control.

## Services

| Service | Description |
|---|---|
| `postgres` | PostgreSQL 15 database |
| `redis` | Redis 7 cache and message broker |
| `api` | FastAPI backend (port 8000, internal only) |
| `worker` | Celery worker for async tasks (moderation, PII detection) |
| `beat` | Celery Beat scheduler (license heartbeat, periodic tasks) |
| `frontend` | Next.js dashboard (port 3000, internal only) |
| `nginx` | Reverse proxy — the only service exposed to the internet (ports 80/443) |

All traffic goes through nginx. No other ports need to be open.

## AWS EC2 Setup

### Recommended instance

`t3a.medium` (2 vCPU, 4 GB RAM) is sufficient for small teams (2–10 users). Use `t3a.large` if you anticipate heavy policy evaluation load.

### Security Group rules

Only open these ports to the internet:

| Port | Protocol | Source | Purpose |
|---|---|---|---|
| 80 | TCP | `0.0.0.0/0` | HTTP (redirects to HTTPS) |
| 443 | TCP | `0.0.0.0/0` | HTTPS |
| 22 | TCP | Your IP only | SSH access |

All other ports (5432, 6379, 8000, 3000) must remain closed — they are internal to the Docker network.

### SSL certificates (production)

`setup.sh` generates self-signed certificates for initial setup. Replace them with real certificates before exposing the service publicly.

**Option A — Let's Encrypt (free, recommended):**
```bash
sudo apt install certbot
sudo certbot certonly --standalone -d yourdomain.com
sudo cp /etc/letsencrypt/live/yourdomain.com/fullchain.pem ssl/fullchain.pem
sudo cp /etc/letsencrypt/live/yourdomain.com/privkey.pem ssl/privkey.pem
docker compose restart nginx
```

Set up auto-renewal:
```bash
# Add to crontab: renew and restart nginx monthly
0 3 1 * * certbot renew --quiet && \
  cp /etc/letsencrypt/live/yourdomain.com/fullchain.pem /path/to/deploy/ssl/fullchain.pem && \
  cp /etc/letsencrypt/live/yourdomain.com/privkey.pem /path/to/deploy/ssl/privkey.pem && \
  docker compose -f /path/to/deploy/docker-compose.yml restart nginx
```

**Option B — AWS ALB (SSL termination at load balancer):**

Put an ALB in front of the EC2, attach an ACM certificate, and terminate SSL at the ALB. nginx then handles HTTP only internally. Update the nginx.conf to remove the HTTPS server block if using this approach.

### DNS

Assign an **Elastic IP** to the EC2 instance so the IP address survives reboots. Point your domain's A record to it.

## Remote LLM (RunPod / cloud vLLM)

Set these in `.env`:

```env
VLLM_URL=https://your-runpod-endpoint-8000.proxy.runpod.net/v1
VLLM_MODEL=your-model-name
MAGPIE_LOCAL_LLM=false
```

The LLM container will not start. All policy evaluation calls route to the remote endpoint.

## Local LLM (GPU host only)

If the host has a compatible GPU:

```env
VLLM_URL=
MAGPIE_LOCAL_LLM=true
```

`setup.sh` will build and start the local vLLM container. This requires NVIDIA drivers and the NVIDIA Container Toolkit installed on the host.

## Common Commands

```bash
# View running containers and health status
docker compose ps

# Tail all logs
docker compose logs -f

# Tail a specific service
docker compose logs -f api

# Restart a service
docker compose restart api

# Stop everything
docker compose down

# Stop and delete all data (destructive)
docker compose down -v

# Update to the latest images
./setup.sh
```

## Updating

Re-run `setup.sh` to pull the latest images and restart services:

```bash
./setup.sh
```

Data volumes (`postgres_data`, `redis_data`) persist across updates — your data is never affected by an image update.

To pin a specific version instead of `latest`, set `MAGPIE_VERSION=0.6.0` in `.env`.

## Troubleshooting

**Services not starting / crash-looping:**
```bash
docker compose logs <service-name> --tail=50
```

**Health check failing:**
```bash
curl http://localhost/health
```
All three of `status`, `database`, and `redis` should be `"healthy"`.

**nginx SSL error on startup:**
The `ssl/` directory is missing or empty. Run `setup.sh` again — it will generate self-signed certificates automatically.

**Redis unhealthy:**
`REDIS_PASSWORD` is likely empty in `.env`. Delete `.env` and re-run `setup.sh` to regenerate all secrets.

**License authentication failed:**
- Verify `MAGPIE_LICENSE_KEY` in `.env` is correct
- Verify `MAGPIE_LICENSE_SERVER=https://license.magpie.so`
- Check that the host can reach `https://license.magpie.so` (outbound HTTPS must be allowed)

**Admin password:**
The admin password is stored in `.env` as `ADMIN_PASSWORD`. It is set once on first startup — changing it in `.env` after first run has no effect. Reset via the dashboard settings.
